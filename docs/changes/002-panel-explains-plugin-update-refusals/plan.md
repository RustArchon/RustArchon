# 002. The Panel explains every plugin-update refusal, and can re-sign the served plugin — Plan

- Status: Complete
- Spec: `spec.md` (Approved, open questions answered "yes" to both: last/next pass shown on both the server page and the Plugin admin page; a signed-by-another-Panel badge on the server header)
- ADRs: none. No accepted ADR is affected (ADR-0006 covers logging; this adds none of its surface). The one design choice that could look architectural (the pass timing is held in memory, not stored) is recorded under Risks.

## Approach
One source of truth for "may an update start on this server?". Today the checks live inline in `ThirdPartyPluginUpdateService.StartAsync`, and `GetOffersAsync` re-implements a weaker subset (freshness + capability). Extract the **server-level preconditions** (server enabled, plan, status present and fresh, signed by a key this Panel knows, key not revoked, plugin has the capability) into a single method that returns a code and a plain-language message, plus a "what to do" hint. `StartAsync` calls it (behavior and codes unchanged); `GetOffersAsync` calls it too and puts the result on each offer (`BlockCode`, `Detail`). Automatic-only gates (opt-in, wipe hold, platform switch) are reported separately, as the automatic updater's status for a server, from the same gate and the same setting the pass reads.

The automatic updater records when each pass ran in a small in-memory singleton; the settings endpoint and a new Plugin admin endpoint expose last/next pass.

For the file: the Plugin admin controller gets a download of the **currently served** plugin/updater signed with the active key (the same signing and audit path `DownloadRelease` already uses, with the source taken from `IPluginReleaseService.ResolveAsync(kind)` instead of a stored release id). The Plugin admin page gets a button on the "serving" line and the install instruction.

## Risks
- **Offer/StartAsync drift again.** Mitigated by routing both through the single preflight and the parity test in step 2; the table test fails when a new refusal code is added without an offer-side explanation.
- **Extracting from `StartAsync` changes a security-relevant path.** Mitigated by keeping codes and order identical and leaving every existing service test untouched and green; I will say so if any needs editing.
- **Pass timing is in memory.** After an Api restart "last pass" reads "not yet run since the Api started" with the next-due time, and with several Api instances each would show its own. Accepted for now (a single Api today); storing it would need a table and a migration, which this change does not justify. Say if you disagree.
- **A download link makes it easy to install the wrong Panel's file.** The page names the Panel and active key fingerprint next to the button so the file can be matched to the key a server reports.
- **Dev database / stack use in step 12** needs your go-ahead at that point, and it needs Visual Studio stopped before any migration (none planned: no schema change).
