# 003. Diagnostic snapshot views, and no unreadable plugin reply goes unrecorded — Plan

- Status: Complete
- Spec: `spec.md` (Approved 2026-10-15)
- ADRs: [0007](../../adr/0007-diagnostic-views-with-deny-list-attribute-and-catalog.md) (Proposed; approved with this plan)

## Approach
**Part A (small, first).** One shared helper logs an unreadable plugin reply (server, command name, bounded start of the reply, run through the existing `LogRedactor`) and returns a new refusal code `unreadable_reply` with a sentence that does not say "too old". The three `ParseReply` copies (third-party updates, plugin/Updater update, map upload) use it. The Panel maps the new code to a localized sentence.

**Part B/C (the views).** A new Api folder `DiagnosticViews/` holds: the `[DiagnosticsHidden("reason")]` attribute (the definitive prohibited list, on entity properties), an entity serializer that returns a listed entity's properties except hidden ones, an `IDiagnosticView` interface (name, version, description, typed parameters, `ExecuteAsync`), a `ViewCatalog` generated by reflection (viewed entities minus hidden properties, plus the view's computed parts), and one view class per initial view. A backstop test fails the build if a viewed entity has a property that looks secret and is not marked hidden. The views use the Api's own repositories and services (`IThirdPartyPluginUpdateService.GetOffersAsync` and `GetServerRefusalAsync`, `IPluginKeyService`, the platform settings cache, `RconEventRepository`), never raw table access from the Panel.

An Api controller `internal/diagnostics/views[/{name}]` (internal-service key, token checked first through the existing `IDiagnosticLogTokenService`, audited) returns the catalog and the view envelope. The Panel gets `GET /diagnostics/views[/{name}]` by generalising the existing log door: the same throttle, header, generic 401, 404-when-off, and the address-behind-Cloudflare rule, forwarded without merging. Views need the Api, so there is no Panel-only fallback.

The envelope is `{ view, version, readAtUtc, data, unavailable[] }`; errors are one shape; responses are size-bounded.

## Risks
- **A view diverges from the Panel's own explanation.** Mitigated by reusing `GetOffersAsync` and `GetServerRefusalAsync` rather than reimplementing them (step 7).
- **Fail-open for unmarked columns (recorded in ADR-0007).** The attribute is the definitive list by the owner's decision, so a new sensitive column that is not marked is returned until something catches it. Mitigations that do not change the decision: the backstop test on secret-looking names and encrypted or binary columns, seeded-secret tests per view, and the revisit trigger in the ADR (an unmarked secret ever returned means moving to an exposed-fields list under a new ADR).
- **A column that looks harmless but is sensitive** (for example a free-text field holding a pasted credential) will not be caught by the backstop; this is the same residual risk and is accepted.
- **Response size.** Each view caps its collections and message lengths and says when it truncated.
- **The token reaches all tenants' servers.** Accepted by the owner's decision; Site Admin-only and platform-wide; revisit trigger is recorded in ADR-0007.
- **The real reply to the update command is still unknown.** Part A makes it visible on the next click; the parse fix itself is a separate bug-fix with a test built from the real reply and is not in this plan.
- **Dev database and stack use in step 12** needs the owner's go-ahead at that point; no schema change is planned, so no migration and no need to stop Visual Studio for one.
